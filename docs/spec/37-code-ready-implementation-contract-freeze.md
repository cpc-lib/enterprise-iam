# Enterprise IAM & Dynamic Authorization Platform
## 37 — CODE-READY Implementation Contract Freeze 1.1

Status: `NORMATIVE`  
Applies to: CODE PHASE 01 and all later stories unless superseded by a reviewed
SPEC/ADR change.  
Keywords `MUST`, `MUST NOT`, `SHOULD` and `MAY` are normative.

## 1. Authority and conflict resolution

Implementation priority is:

1. SPEC 37 and machine-readable contracts referenced here;
2. SPEC 36;
3. SPEC 24–35;
4. SPEC 01–23.

Within the same level, security takes precedence over availability and a
restrictive decision takes precedence over a permissive decision. A conflict
MUST create an ADR or Spec issue; it MUST NOT be resolved silently in code.

The following files are normative for CODE PHASE 01:

- `docs/api/openapi-code-phase-01.yaml`
- `docs/events/asyncapi-code-phase-01.yaml`
- `docs/security/SECURITY-PARAMETERS.yaml`
- `docs/database/code-phase-01/*.sql`
- `docs/architecture/REQUIREMENTS-TRACEABILITY.csv`

## 2. Scope lock

CODE PHASE 01 implements one vertical security loop:

```text
tenant bootstrap
→ user/role creation
→ role binding and permission grant
→ login and refresh rotation
→ authorization check
→ revoke and immediate deny
→ explain/audit correlation
```

Team roles, data/field permissions, sharing and files remain in the V1 roadmap
but MUST NOT expand the first phase's schema or runtime path unless required by
an approved compatibility decision.

## 3. Identifier and representation rules

- Persistent IDs are unsigned 64-bit values generated by the application.
- JSON serializes every 64-bit ID as a decimal string to prevent JavaScript
  precision loss.
- Timestamps use RFC 3339 UTC with millisecond precision.
- Database timestamps use `DATETIME(3)` and the connection/session timezone UTC.
- Enum values are uppercase ASCII and additive changes only are compatible.
- Unknown enum values at a service boundary MUST fail validation, never map to
  a privileged default.

## 4. Tenant isolation invariant

For every tenant-owned read and write:

```text
effectiveTenantId = trusted token/session context
SQL predicate includes tenant_id = effectiveTenantId
resource tenant_id is checked before mutation
```

Client-supplied `X-Tenant-Id`, forwarded identity headers, body tenant IDs and
query tenant IDs are untrusted. Gateway MUST remove such external headers and
write a signed/internal trusted context. Downstream services MUST reject a
missing or invalid trusted context. Cross-tenant lookup returns `404` when
resource visibility would otherwise be disclosed.

## 5. Authentication contract

- Login responses MUST be indistinguishable for unknown identity and wrong
  password except for trace data available only internally.
- Password verification MUST use the parameters in
  `SECURITY-PARAMETERS.yaml`; stored values MUST be PHC-format hashes.
- Access JWT verification MUST pin the algorithm and validate `typ`, `iss`,
  `aud`, `exp`, `nbf`, `iat`, `jti`, tenant, subject and session claims.
- Tokens of different kinds MUST use mutually exclusive `typ` and `aud`
  values. Refresh tokens are opaque, random, stored only as keyed hashes and
  rotated on every use.
- Refresh-token reuse MUST atomically revoke the token family/session, advance
  user security state and emit `RefreshTokenReuseDetected.v1`.
- Logout, force logout, user disable and password change MUST invalidate the
  affected session path before returning success.

## 6. Authorization contract

Default decision is `DENY`. Unknown APIs, disabled resources/operations,
missing mappings, unsupported policies, stale revoke fences and unavailable
authoritative dependencies MUST deny.

Every decision input contains:

```text
tenantId, subjectId, sessionId, resourceId, operationId,
resourceInstanceId?, context, permissionVersion, requestId
```

The decision output contains:

```text
decision, reasonCode, decisionId, permissionVersion,
matchedGrantIds[], obligations{}, evaluatedAt
```

An allow decision is valid only for the exact tenant, subject, resource,
operation and instance context evaluated. Cache keys MUST include those
dimensions plus all policy-relevant context and permission version. Negative
cache entries MUST have a shorter or equal TTL than positive entries.

## 7. Permission mutation and immediate revoke

All grant/revoke mutations MUST:

1. lock or version-check the aggregate;
2. update binding state;
3. monotonically increment the tenant/subject permission version in the same
   local transaction;
4. insert a versioned outbox event in that transaction;
5. return only after authoritative storage commits.

The runtime authorization path MUST compare the presented/cached version with
the authoritative fast-path version. A lower, missing or unparsable version is
stale and MUST deny or force synchronous rebuild; it MUST never allow.

## 8. HTTP contract

- OpenAPI is the Controller and client-generation authority.
- Mutating endpoints require `Idempotency-Key` unless explicitly excluded.
- `Idempotency-Key` scope is `(tenant, subject, route, key)` and the stored
  request fingerprint is method + normalized route + canonical body hash.
- Same key and fingerprint returns the original status and body; same key with
  a different fingerprint returns `409 IAM_IDEMPOTENCY_KEY_CONFLICT`.
- Error bodies never expose stack traces, SQL, policy internals, existence of
  hidden resources, raw tokens or secrets.
- Every response and event MUST be correlatable by `traceId`/`correlationId`.

## 9. Event contract

Events use `asyncapi-code-phase-01.yaml`. Consumers MUST:

- validate envelope and event version before business handling;
- deduplicate by `(consumer_name, event_id)`;
- reject tenant mismatch between envelope and payload;
- apply monotonic aggregate/version checks;
- acknowledge only after local effects commit;
- route poison messages to a controlled DLQ without logging sensitive payloads.

Incompatible payload changes require a new event name/version and a documented
dual-publish/dual-read migration.

## 10. Database contract

- Each service owns its database and Flyway history.
- No runtime cross-database join or write is allowed.
- Tenant-owned unique constraints include tenant identity.
- Logical-delete uniqueness uses `delete_marker`; active rows use marker `0`,
  deleted rows use their own non-zero ID.
- Foreign keys MAY be used only inside one service database and MUST NOT cross
  bounded contexts.
- Application mutation, permission version and outbox insert are one local
  transaction.
- Migration scripts are immutable after any shared environment applies them.

## 11. Observability and privacy

Required structured fields:

```text
timestamp, level, service, environment, traceId, requestId,
tenantIdHash, subjectIdHash, routeTemplate, outcome, errorCode
```

Authorization telemetry additionally contains decision ID, resource/operation
IDs, reason code, permission version and latency. It MUST NOT contain password,
access/refresh token, cookie, authorization header, raw identity, policy secret
or unmasked protected field.

## 12. Security baseline

The project targets OWASP ASVS Level 2. Authorization and administrative
functions apply the higher-risk controls identified by the threat model.
JWT processing follows RFC 8725 algorithm verification, explicit typing,
audience separation and key-entropy requirements. API tests MUST cover object,
function and property-level authorization and resource-consumption limits.

External OAuth/OIDC authorization-server conformance and FAPI 2.0 are not
silently implied by this IAM scope; adopting them requires an explicit scope
and interoperability ADR.

## 13. Verification evidence

A story is done only if its traceability row contains:

- normative requirement ID;
- API/event/schema artifact;
- unit and integration test ID;
- negative/security test ID;
- CI evidence URL or immutable build ID.

Required CODE PHASE 01 security properties:

1. Same request produces the same decision at the same permission version.
2. Cross-tenant subject/resource combinations never allow.
3. Removing a grant cannot increase effective rights.
4. User disable, session revoke and permission revoke converge to deny within
   the frozen security bound; critical paths are immediate before success.
5. Unknown API/resource/operation/policy/dependency state denies.
6. Duplicate commands/events do not duplicate business effects.
7. A reused refresh token revokes the whole affected family.

## 14. Change control

Breaking changes require:

1. ADR and threat-model delta;
2. contract version and compatibility analysis;
3. expand/contract migration plan;
4. consumer/client migration evidence;
5. rollback plan;
6. updated traceability and release gate.

Code that contradicts this freeze is a defect, not an undocumented design
choice.

## 15. CODE PHASE 01 exit gate

- Gate B in `CODE-PHASE-ENTRY-GATE.md` is green.
- OpenAPI/AsyncAPI validation and compatibility checks are green.
- Flyway migration applies to a clean database and is idempotent at the runner
  level (second run has no pending migration).
- Golden loop and all seven security properties above pass using real MySQL
  and Redis containers.
- Authorization deny-path remains functional during Redis cache loss; unsafe
  degradation does not occur.
- Audit and decision correlation is demonstrated for allow, deny and revoke.
- No P0/P1 threat-model test is skipped.

Only then may the next authorization capability enter implementation.
